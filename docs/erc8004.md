# ERC-8004: agent identity and reputation

SEN-27. Every hired agent is minted an identity on the **ERC-8004 Identity
Registry** and, as its theses settle (SEN-22), each verdict is written to the
**Reputation Registry** as realised PnL in basis points. The point is a public,
portable track record: an agent's history is readable by anything that speaks
ERC-8004, not only by Sente.

Code: `services/api/src/agents/reputation/erc8004.ts`. Live probe:
`services/api/scripts/erc8004-live.ts`.

## Addresses

|                       | Identity Registry                            | Reputation Registry                          |
| --------------------- | -------------------------------------------- | -------------------------------------------- |
| Monad testnet (10143) | `0x8004A818BFB912233c491871b3d84c89A494BD9e` | `0x8004B663056A597Dffe9eCcC1965A193B7388713` |
| Monad mainnet         | `0x8004A169FB4a3325136EB29fA0ceB6D2e539a432` | `0x8004BAa17C55a88189AE136b182e5fdA19dE9b63` |

**The mainnet addresses have no code on testnet and the testnet ones have no code
on mainnet.** The SEN-27 plan's first draft used the mainnet pair on testnet,
where `eth_getCode` returns `0x`. They are exported as constants only; nothing
picks them by chain id, and this API has no mainnet RPC, key or treasury.

One agent's globally unique handle, per the spec, is
`{namespace}:{chainId}:{identityRegistry}` — `agentRegistryId()` in the module
returns `eip155:10143:0x8004A818…` for testnet. It is what a reputation
aggregator keys an agent by when it is registered on several chains.

Verified on testnet, 2026-09-17, read-only:

- `eth_getCode` returns 130 bytes at both testnet addresses (small proxies).
- `getIdentityRegistry()` on the Reputation Registry returns exactly the
  `ERC8004_IDENTITY_REGISTRY` constant.
- Agents `#0` … `#31` are already minted by other parties (32 of them), each
  with an owner, so the deployment is live and in use.
- A **simulated** `register(string)` (an `eth_call`, so nothing was minted)
  returns `agentId` `1874`, i.e. the next id the real registration would get,
  and `eth_estimateGas` accepts the exact calldata the module builds.

## Environment

All of it is in `.env.example` (SEN-36), with the defaults below; this table is
the reference for what each one means.

| Variable                 | Meaning                                                                                                                                                                                 |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ERC8004_REGISTRAR_KEY`  | **Required to enable.** A funded EOA that signs `register` and therefore OWNS every agent NFT Sente mints. Absent: agents are hired without an on-chain identity, exactly as before.    |
| `ERC8004_REVIEWER_KEY`   | The funded EOA that signs `giveFeedback`. **Must not be the registrar** — see below. Absent: identity works, reputation is refused with `reviewer_unconfigured`.                        |
| `ERC8004_AGENT_BASE_URL` | Where an agent's Ledger lives. Default `https://sente.lol`, so the registration file points at `https://sente.lol/agents/{id}`.                                                         |
| `ERC8004_MCP_ENDPOINT`   | The shared MCP endpoint advertised in the registration file's `services`. Optional.                                                                                                     |
| `ERC8004_IMAGE_URL`      | The registration file's `image`. Optional, and deliberately omitted rather than invented: today Sente hosts no agent image, and a URL that 404s is worse than a missing optional field. |
| `ERC8004_REGISTER_GAS`   | Fixed gas limit for `register`. Default `950000`.                                                                                                                                       |
| `ERC8004_FEEDBACK_GAS`   | Fixed gas limit for `giveFeedback`. Default `350000`.                                                                                                                                   |
| `MONAD_TESTNET_RPC_URL`  | Reused for the reads and writes, like every other Monad path.                                                                                                                           |

A malformed key throws at boot (`… is not a 0x-prefixed 32-byte hex private
key`), and the message never echoes the value. A _missing_ key is not an error:
unconfigured ERC-8004 is a valid deployment, `POST /agents` still works, and the
agent simply has no `erc8004AgentId`.

## Who gives feedback: there are two keys, and the second one is not optional

The spec says it plainly:

> The feedback submitter **MUST NOT** be the agent owner or an approved operator
> for `agentId`.

Measured on the live testnet deployment: a `giveFeedback` simulated from the
owner of agent `#0` reverts with

```
Execution reverted with reason: Self-feedback not allowed.
```

Since `ERC8004_REGISTRAR_KEY` signs `register`, **the registrar is the agent's
owner** and can never be its reviewer. So Sente writes identity from one key and
reputation from another, and with only the registrar configured it REFUSES to
write feedback rather than sending a transaction it knows will revert — Monad
charges the gas limit for a reverted transaction (CLAUDE.md gotcha 4), so an
attempted self-feedback is a pure loss.

That split is also the honest framing of the protocol: the reviewer is the client
that hired the agent and saw the fills, and it is not the party being reviewed.
`ERC8004_REVIEWER_KEY` is that client: a Sente service EOA, not the user and not
the agent's wallet. Two consequences worth knowing and documenting:

- A reviewer's reputation is per-key. `getSummary`/`getClients` filters by
  `clientAddress`, and a fresh reviewer key starts at zero entries. Rotating the
  reviewer key therefore loses the review history it accumulated — for some
  aggregators that is exactly what "filter by reviewer" is for, and Sente's
  reviewer is publicly named in this file and in the logs.
- Nothing here is sybil-proof. Sente reviewing its own agents is a single
  reviewer with a single voice; the registry's design answer is that clients
  filter by reviewer, and ours is public. Do not present these entries as
  independent third-party reputation.

## What a hire registers

`register(agentURI)` where `agentURI` is a base64 `data:` URI — the spec's
fully on-chain form, so nothing has to be hosted. The file is built in
`agentRegistrationFile`:

```json
{
  "type": "https://eips.ethereum.org/EIPS/eip-8004#registration-v1",
  "name": "Momentum",
  "description": "anthropic/claude-sonnet-5 trading agent on Monad, run by Sente. Strategy: … Mandate: venues kuru+perpl; …; max order 250; expires 2033-05-18 Wallet: 0x… Ledger: https://sente.lol/agents/…",
  "services": [
    { "name": "web", "endpoint": "https://sente.lol/agents/{id}" },
    { "name": "MCP", "endpoint": "https://api.sente.lol/mcp", "version": "2025-06-18" }
  ],
  "x402Support": false,
  "active": true,
  "registrations": [],
  "supportedTrust": ["reputation"]
}
```

Three deliberate choices:

- **`registrations` is empty.** The `agentId` is assigned BY the registration
  transaction, so it cannot be in the URI that same transaction carries. Filling
  it in needs a second `setAgentURI` transaction; not worth the gas today, and
  the Ledger link is already in the file.
- **The mandate is summarised in words, not atoms.** `maxDepositAtoms` and
  `maxCollateralAtoms` are raw token atoms; printing `1000000000` without the
  token's decimals would be a false statement about size. Markets, leverage, the
  max order notional and the expiry are exact.
- **The description and the name are capped** (`MAX_DESCRIPTION_CHARS` 320,
  `MAX_NAME_CHARS` 64, the latter matching `AGENT_NAME_MAX_LENGTH`). That is a
  gas bound, not tidiness: the file is calldata, and the fixed gas limit is only
  a bound because the file is bounded. A spec pins the largest URI the builder
  can produce (`ERC8004_MAX_AGENT_URI_CHARS`, 1,125 chars) against the length the
  limit was measured at.

The registrar key signs, never the agent's Privy wallet: the mandate is the
user's contract with the agent, and minting an NFT is not something the mandate
should have to permit. The agent's wallet address appears in the file because it
is public anyway.

## What a verdict writes

Every `verdict` event (SEN-22) is published as one `giveFeedback` entry:

| field                                     | value                                                                 |
| ----------------------------------------- | --------------------------------------------------------------------- |
| `agentId`                                 | the agent's `erc8004AgentId`                                          |
| `value`                                   | realised PnL in **basis points of the thesis's own cost basis**, ×100 |
| `valueDecimals`                           | `2`                                                                   |
| `tag1`                                    | `pnl`                                                                 |
| `tag2`                                    | the venue: `kuru` or `perpl`                                          |
| `endpoint`, `feedbackURI`, `feedbackHash` | empty                                                                 |

`value` with `valueDecimals` 2 reads as basis points with two decimals:
`25000` is 250.00 bps = +2.50% on the notional the thesis opened, and a losing
thesis is negative (the spec's own `tradingYield` example does the same). Basis
points, because `pnlAsset` differs per venue — USDC on Kuru, AUSD on Perpl — and
a raw amount is not comparable across them; the ratio is. The arithmetic is exact
BigInt in `pnlBasisPoints`, round-half-away-from-zero, and a verdict whose cost
basis is zero or absent writes **nothing**: the ratio has no meaning there, and
`0` would say "flat" about a trade that may have made or lost money.

### Which PnL, exactly (SEN-33)

A verdict's `realisedPnl` is **net of the fees the thesis's own fills paid, on
both venues**. On Kuru that is FIFO price PnL less the taker fees; on Perpl it is
the venue's `dpnl` less funding and then less those same fees, because `dpnl` is
_price_ PnL and does not include them. One row, one definition — before SEN-33 a
Kuru verdict was net and a Perpl verdict was gross, so the two could not be read
side by side. (The leaderboard's own `realisedPnl` column is a different number
from a different source — the indexer's gross figure, `docs/leaderboard.md` — and
both readings travel with their own notes for exactly that reason.)

Perpl's `realizedPnl` and `fundingPaid` are **cumulative over the position's
life** (`packages/venues/src/types.ts`), and `close_position` can be partial, so
a verdict is credited only with the MOVEMENT since the previous close of **that
position**. Two theses that share one position therefore split it instead of
each being paid the whole figure.

Which position is not inferred: the close event carries `positionId`, the
venue's own id (Perpl's `pid`), set next to the two figures it qualifies. So a
position that carries on and a position that ended and was replaced are told
apart rather than guessed at — a liquidation between two theses on one market
cannot leave a stale baseline for the next one to be measured against. A close
that names no position (one logged before SEN-33, or one whose final frame never
arrived) falls back to a per-market baseline that is dropped whenever a position
closes. What a verdict could not account for — size closed with no lot of its own
behind it, or a venue figure read as a movement — is spelled out in the verdict's
`notes`, which the Ledger can show next to the number.

A thesis is settled **by agent and market, across runs**. A scheduled agent
records its thesis in one tick and closes the position in a later one, so a
run-scoped settle left every such thesis open for ever and published no feedback
at all. One thesis still gets one verdict: a fill whose thesis already has a
`verdict` event on the log records nothing.

**Any fill can settle a thesis, not just `close_position`** (SEN-47). That tool
is Perpl-only, and a Kuru thesis ends when its own fills net back to zero — so
while the close was the only place a verdict was appended, every spot round trip
was settled by the leaderboard (which calls `settle` itself) and invisible to
both consumers that read the `verdict` EVENT: the Ledger and this registry. A
verdict settled by a fill also carries that fill's `blockNumber`, which is all
the events route needs to draw a consensus ramp under it (SEN-35).

The three empty fields are the spec's optional ones, and they are left empty on
purpose. Sente hosts no per-feedback JSON document, so pointing `feedbackURI` at
the events route and hashing it would imply an integrity guarantee that expires
the moment the log grows. The `agentURI` carries the Ledger link instead, and
that is where the fills behind the number are readable.

### Where it hooks in

The Tool Runner and the `/mcp` server both append through the same
`AgentEventLog`, and every verdict is appended in one place inside the gate
(`recordVerdict`, reached by any write that filled) — so SEN-27 decorates the
LOG (`ReputationEventLog` in `erc8004.ts`), not the tool.
That is one place to keep in sync instead of two surfaces, and it is why
`agentToolsProviders` binds `AGENT_EVENTS` to the decorated log.

`append` returns as soon as the event is stored. The registry write is queued
inside `Erc8004Reputation` and never rejects: a close that landed must not be
reported to the model as failed because a registry was slow, and a stored verdict
must survive a registry that is down. A spec awaits `whenIdle()`. One thesis is
published once per process (`agentId:thesisSeq`); the guard is in memory, like
every other store in this API, so a restart could re-publish a verdict if it were
replayed — the registry would then hold a duplicate entry rather than a wrong one.

## Failure behaviour

Nothing in `erc8004.ts` throws to its callers.

| Situation                                                   | Outcome                                                                                                                              |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| No `ERC8004_REGISTRAR_KEY`                                  | `registerOnHire` → `not_configured`; the hire succeeds, `erc8004AgentId` unset                                                       |
| Registrar RPC/broadcast/revert fails                        | `write_failed`; the hire succeeds, an ERROR is logged with the message                                                               |
| Registrar broadcast but no receipt                          | `write_failed` after the timeout, **no retry**: a second `register` would mint a SECOND agent, and an unconfirmed one may still land |
| No `ERC8004_REVIEWER_KEY`, or the reviewer is the registrar | `self_feedback_refused` / `reviewer_unconfigured`; no transaction is sent                                                            |
| Agent has no ERC-8004 id                                    | `not_registered`                                                                                                                     |
| Thesis still open                                           | `thesis_open`                                                                                                                        |
| Cost basis zero or not a decimal                            | `notional_unknown`                                                                                                                   |
| `\|value\|` outside int128                                  | `notional_unknown` (same refusal: no honest number)                                                                                  |
| Same thesis published twice in-process                      | `duplicate`                                                                                                                          |
| `giveFeedback` fails                                        | `write_failed`; the verdict is still on the log                                                                                      |

Both keys are ordinary EOAs sending contract calls, so a lone send is unaffected
by Monad's 10 MON reserve balance (gotcha 12) — but a reverted send is charged
its full limit, and the second send from an under-reserve key inside the window
is exactly what the rule bites. Writes are therefore serialised per key, one
transaction in flight, with an explicit nonce that never goes backwards (the
public RPC is load balanced), and no retry on another key.

## Gas

Monad charges `gas * gasPrice` on the LIMIT, not on gas used (gotcha 4), so both
limits are measured constants, never `estimateGas` at runtime. Measured
2026-09-17 against the live registries with the exact calldata the module builds:

| call                                                                 | measured          | limit   |
| -------------------------------------------------------------------- | ----------------- | ------- |
| `register(string)`, typical 833-char URI                             | 685,052           | 950,000 |
| `register(string)`, largest the builder can produce (1,125-char URI) | 849,887           | 950,000 |
| `giveFeedback(...)`, across agent ids and clients                    | 278,412 – 295,694 | 350,000 |

At ~122 gwei a registration costs about 0.10 MON and a feedback about 0.04 MON.
The registrar and reviewer are funded from the treasury; they are separate keys
on purpose, so one key's balance problem cannot take down both halves.

## Running the live check

```bash
mise exec -- pnpm --filter @sente/api run erc8004:live                  # read-only, no key
mise exec -- pnpm --filter @sente/api run erc8004:live -- --register     # mints a probe agent
mise exec -- pnpm --filter @sente/api run erc8004:live -- --feedback 1874 --bps 250
```

The read-only mode needs no key: `--register`/`--feedback` need
`ERC8004_REGISTRAR_KEY` / `ERC8004_REVIEWER_KEY`, and both refuse when the
registrar's balance cannot cover `gas * maxFeePerGas` (a message, rather than a
revert charged at the limit). The probe is written for the public testnet RPC's
15-requests-a-second limit — bulk reads are spaced, so rate-limit errors do not
read as a broken deployment.

### Still outstanding

- **No transaction has been sent.** The registrar and reviewer keys do not exist
  yet (`.env` has neither `ERC8004_REGISTRAR_KEY` nor `ERC8004_REVIEWER_KEY`), so
  the acceptance criterion's "a hired agent gets an `agentId` on testnet and a
  feedback entry after a verdict, tx hashes recorded" is proven by simulation and
  gas measurement, not by a confirmed transaction. Two funded EOAs and one run of
  `--register` plus `--feedback` close that gap; record the two hashes here.
- **The registrar owns every agent it registers.** If Sente is ever to hand
  ownership to the user (the ERC-721 way), that is `transferFrom` from the
  registrar to the owner's smart account — a deliberate, separate change; nothing
  here assumes ownership stays with Sente.
- **An amended mandate does not update the published file.** The URI is built
  from the record as hired; refreshing it is `setAgentURI` (another transaction).
- **The Ledger does not render the id yet.** `toAgentResponse` exposes
  `erc8004AgentId` since SEN-36 and `apps/mobile/src/agents/api.ts` carries the
  field, so the app has the on-chain id; drawing it (and a link to the registry)
  is a mobile change nobody has made.
- **The Validation Registry is out of scope**: it is unofficial on Monad, and the
  SEN-27 plan says to skip it.
