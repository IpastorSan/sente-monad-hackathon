# Sente test-suite audit — do the tests test real scenarios with value?

Date: 2026-09-27. Repo: `/home/ignacio/Work/moveseventyeight/sente` at `00b2387` (audit started at `5f01625`; SEN-78/101/102/103 landed mid-audit and were folded in). Read-only: nothing in the main checkout was touched. Mutations ran in throwaway copies under `/tmp/claude-1000/audit-wt*`. Method: read every suite in the money/security paths, run **~95 source mutations** across five copies and record killed/survived, and build one throwaway cross-side probe (planner → phone verifier).

## 1. Executive summary

**Overall verdict: good, and unusually honest for a codebase this young.** The suites overwhelmingly test behaviour at the boundaries that matter (what gets signed, what gets refused, which receipt flag decides), with hand-written fakes at the network edge rather than mocks of the code under test, fixed clocks, no network. Of ~95 mutations, **~74 were killed**. The survivors cluster in a few identifiable places, and the highest-risk items are **two design holes that no test could have caught because the behaviour itself is wrong**, plus **one structural gap**: the server→phone trade contract is pinned by mirrored fixtures and comments, never by running the real planner output through the real verifier.

Green and fast: `mise exec -- pnpm run test` → presets 62, venues 98, mandate 48, mobile 515 (1 skipped, live-RPC gated), api 1112 → **1,835 tests, 11.2 s wall** (api 9.0 s). Re-run at `00b2387`: mobile 564/1 skipped, api trade+portfolio 98/98.

## 2. Per-area findings

### 2A. Phone-side signing checks (`apps/mobile/src/trade/*`) — **strong**

This is the security boundary for manual trades and it is the best-tested code in the repo. Every module has one accepted shape and one tampered payload per rule, refusals assert the _reason_ via regex, no network, no clocks.

**Fixture independence — mostly good, one caveat.**

- `calls.test.ts:48-53, 116-129, 160-168` builds accepted fixtures with **`permissionless`'s `encode7579Calls`** — the server's actual encoder (`kuru-planner.ts:430-440`) — and the decoder re-encodes with the phone's own `encodeKernelExecute`. So a bug shared by both sides cannot pass silently: the two encoders are genuinely different code.
- `kuruLegs.test.ts:92-137` pins each hand-written ABI fragment's selector to the **Kuru SDK's** full ABI and asserts the SDK has exactly four `batch` overloads (a new overload in an SDK bump fails the test). Refused functions (`withdrawFromAccount`, builder-fee `batch`, `transfer`) are encoded with the SDK ABI — exactly what a compromised server would reach for.
- `kuruMarket.test.ts:60-82, 103-133` checks `worstPriceUnits`/`depositCapAtoms` against the adapter's `kuruSlippageBound`/`quoteReserveAtoms` on >1000 grid points. This is a differential test, not a tautology, because the two implementations differ (bps/bigint vs Decimal/WAD).
- **Caveat:** `envelope.test.ts:36-56`, `verifyKuru.test.ts:157-184` and `flow.test.ts:88-112` all _mirror_ the server's `sponsoredSendBody(sponsoredCallTransaction())` by hand. The only cross-side pin is `trade.service.spec.ts:195-203` reading `envelope.ts` as text for the idempotency-key template. See finding #4.

**Mutation results (27 run in `/tmp/claude-1000/audit-wt`):**

### 2B. Server trading path (`services/api/src/trade/*`) — **strong, one gap**

- **Planner (`kuru-planner.spec.ts`)** decodes the produced calldata with the venues package ABIs and asserts the money-shaping rules: only the shortfall is deposited and approved exactly (`:166-184`), maker vs taker headroom (`:222-229`), 10 MON reserve with a 1009.9/1010 boundary pair (`:263-273`), deposit-cap boundary pair (`:275-280`), cancel only when the slot still holds _this_ order (`:317-330`), withdraw ≤ free (`:346-352`). Mutations: 8/10 killed (`>`→`>=` on cap, fee swap, reserve `<`→`<=`, live-order check, full-reserve deposit, try-mode, clientOrderId hashing, withdraw boundary). Survived: `maxQuoteNotional` check removed (`kuru-planner.ts:223`), min-notional `<`→`<=` (`:216`, no exact-boundary case).
- **Service (`trade.service.spec.ts`)** uses the **real** `PrivyUserWalletProvider` over a real `PrivyClient` (reaches nothing) and the real `TradeStore`, so the envelope bytes the phone will see are the real ones (`:167-192`). Idempotency (same intent → same trade, different → 409, expired → fresh), ownership (`trade_not_found` for Bob, never 403), miscounted commit leaves the trade committable, and **reconcile-on-read decides from `receipt.success`, never the bundle tx** (`:366-372`). Mutations 5/5 killed (signature count, reconcile always-included, hash ignoring `sizeAtoms`, key template drift, expired prepare returned).
- **Store** and **executor**: exactly-once claim, per-user visibility, retention never forgetting an executing trade, strictly sequential sends with each signature on its own stored request, timeout → `unknown` never `failed`, network error → `unknown` vs Privy answer → `not_sent`, per-wallet mutex against interleaving (`step-executor.spec.ts:127-149, 170-180, 212-234, 261-281`). Mutations 8/8 killed.
- **Gap (finding #4):** the planner is `jest.mock`ed in the service spec and the phone verifier is never invoked from the API side. The probe I built shows this is feasible today in ~120 lines under `apps/mobile` (node `--conditions=source` can import `services/api/src/trade/kuru-planner.ts`, `wallet/send/sponsored-send.ts` and `agents/privy/privy.client.ts` directly — all erasable syntax per gotcha 10). All 15 scenarios pass: buy limit with USDC shortfall, post-only, IOC buy at taker rate, native-MON sell, sell with MON already free, cancel, withdraw — each unbatched and atomic.
- **Missing:** no HTTP-level test of `TradeController` (guard ordering `TradingEnabledGuard` → `ValidationPipe`, `SessionAuthGuard` applied, DTO 400s over the wire); `markets.controller.spec.ts` has the `createNestApplication` precedent. `trade.module.spec` only checks wiring.

## 3. Cross-cutting

**Network / time / randomness:** no suite hits the network (live probes are env-gated: `kernel.test.ts:114`; `refusal-demo` stubs `fetch` to throw). Real-clock dependencies: `operation-tracker.spec.ts`, `consensus.service.spec.ts`, `privy-kuru-submitter.spec.ts:103`, `GasDripService` (no injectable clock), `agents.service.spec.ts:44` epoch fixture (2033). Randomness: `flow.ts` `randomUUID` is injectable (`opts.newClientTradeId`); fine.

**Where property-based tests (fast-check) would pay off — concrete properties:**

- _Trade contract:_ for random valid `KuruPlaceIntent` × fake book state, `verifyKuruTrade(prepare(planKuru(intent)))` is `ok` — and for any single-field tamper of the plan, it is not. (Turns the probe into a generator.)
- _Slippage bounds:_ buy bound ≤ best·(1+s) and on-tick; sell bound ≥ best·(1−s) and on-tick; phone `worstPriceUnits` == adapter `kuruSlippageBound` for random `(best, bps, tick)`, not just the grid.
- _Encoders/decoders:_ `decodeTransactionCalls(encode7579Calls(calls))` round-trips for random call lists; `classifyKuruCall(placeOrderCall(o))` echoes `o`; any byte appended/flipped is refused.
- _FIFO:_ `realised + cost(open lots) == Σ sell proceeds − Σ buy cost` (no fees); `settle().realisedPnl == fifoCostBasis().realisedPnl` on single-thesis histories (would catch finding #3).
- _Decimals:_ `parseAmount(formatAtoms(a,d)) == a`; `sumDecimals`/`compareDecimals` vs a bigint oracle; `fromScaled(toScaled(x,d),d)` canonical; `floor ≤ exact ≤ ceil`.
- _Policy:_ `allows(compileMandate(m), tx)` iff amount ≤ cap ∧ `to` allowlisted ∧ chain 10143 ∧ within expiry ∧ `transfer.to == returnTo`; `compileRevocationRules` allows nothing else (replaces "compiler as its own oracle").
- _Ledger/spacing:_ drip total never exceeds the daily cap over random claim/release/confirm sequences; `WriteSpacer` sends ≥ `spacingMs` apart; `NonceManagedSender` nonces unique under random broadcast failures.
- _Geometry/format:_ `yOf` monotone, values in `[top,bottom]`, never NaN in a path; signed-money formatter never emits `−0`.
